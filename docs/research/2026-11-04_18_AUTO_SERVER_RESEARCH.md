# Auto-battle: legacy Go server behaviour and H5 port gaps

Legacy repo: `E:\mcgame` (paths below are relative to it). Port paths relative to `E:\magiccampus`.

## 1. Summary

The legacy server has **no auto-battle brain**. `battleAuto` / `battlePetAuto` exist only in the Flash client
(`docs/client/logic/Battle.as:94`, `:353`); they read `GamePredef.GLOBAL_SETTING` (the login `interfaceData`) and emit ordinary
`battleUpdateCmd` commands (attack / skill / item). The server only (a) stores the settings (`uif`, `us`, `skillSetBattle`),
(b) hands them back at login, (c) treats a literal `-110` as a plain attack, and (d) fills missing pet commands with a frontline attack.
The "unlimited auto" and the 150-round auto cap are client-only (`docs/memory/battle-combat.md:442`). The server has no VIP gate,
no round cap for PvE (PvP only 30), no potion-in-auto logic of its own. The launcher "autopilot" is a separate server-side bot that
builds an auto command from the same settings (section 6).

## 3. Rules

1. **`-110` constant**: `ClientActionAuto = -110` (`internal/domain/combat/turn_processor.go:30`).
2. **-110 executes as a plain attack**: `turn_executor.go:47-48` `case ClientActionAuto: return tp.executeAttack(actor, cmd)` (basic
   attack skill 1001 on `cmd.TargetID`; target resolved by `resolveAttackTarget`; if the target is nil it is a miss action, `:69-82`).
   The `default` branch also attacks (`:59-60`). It never casts skills or uses items.
3. **Client rarely sends -110**: `Battle.battleCmd` with action -110 and a cached `_lastCmd` resends the last full command array
   instead (`Battle.as:1120-1124`); a bare `-110` is sent only when there is no pet (`Battle.as:372`, `PetCmdCanvas.as:399`) or no `_lastCmd`.
   So the server sees ordinary attack/skill/item commands from auto.
4. **-110 is excluded from deadline anchoring**: `anchorsRoundDeadline` returns false for an all-AUTO batch (`commands_wait.go:118-125`,
   used `commands.go:160`) because the autopilot sends it even during playback.
5. **`ActionTypeAuto` (=6, `domain/combat/battle.go:61`) is an internal, different thing**: lost-turn / skip / DOT marker, never sent
   to the client (`playback_rounds.go:230`). Do not confuse it with client action -110.
6. **Pet command auto-generation** (`generatePetCommands`, `turn_processor.go:218-247`): runs inside `GenerateNPCCommands` (`:215`) at
   the start of every `ProcessRound` (`:260`). For each alive player-side pet participant with no command: target = `SelectFrontlineTarget(enemy)`,
   else `SelectRandomTarget(enemy)`; no target -> `ClientActionTimeout`; else `ClientActionAttack`, `SkillID 0`. So pets never block a round.
7. **Round readiness**: round runs only when every alive human player character has a command (`MissingPlayerCommandActors`,
   `commands.go:158`); pets excluded. Otherwise the reply is `{success:true, battleId, round, waitingForCommands:true, missingActorIds}`
   (`commands_wait.go:15-28`).
8. **Empty ping (no payload)**: round 1 and `BootstrapAutoDefendFired` false -> `autoGenerateDefendCommands` (`commands_wait.go:43-59,78-116`):
   despite its name it builds **ATTACK on the frontline** for every alive player-side participant (only own char + pet when >1 human),
   `DEFEND` only if no enemy target. Later empty pings with no pending commands and a living player side also fire this
   (`shouldAutoDefendEmptyPing` `:43-59`); otherwise "stale empty ping" returns the waiting reply (`commands.go:116-124`).
9. **Turn timeout**: round opens with `TurnTimeout` 63 s backstop; first non-AUTO submission re-anchors all deadlines to `SubmitWindow` 33 s
   (`docs/memory/battle-combat.md:799`). Missing actors get `ClientActionTimeout`, executed as a **defend** (`turn_executor.go:45-46,328-339`
   returns `ActionTypeDefend`); submitted commands are kept (`battle-combat.md:802`). Stale-deadline guard by round number (`:800`).
10. **Skill level -1 resolution**: auto slots send base skill id with `level: -1` (`battle-combat.md:224`).
    - Pet: `resolvePetSkillCommand` (`combat/pet_skill_level.go:31-53`): only for actor = caller's pet and `ActionType == SKILL`;
      `ResolveOwnedSkill(pet, skillId)` returns (ownedId, level) = highest owned skill of the same `code_name`; `SkillID = ownedID`;
      `SkillLevel = level` only when command level <= 0. A skill the pet does not know (not learned id / lower level / variant, `PetOwnsSkillOrVariant`)
      is downgraded to attack (`:45-48,55-64`; `downgradeToAttack` sets action -10, skill 0, level -1, `commands.go:42-46`).
    - Character: ownership check `HasSkill` (`commands_parse.go:94-110`); `HasSkill` also accepts a lower level of a learned family
      (same `code_name`, learned level >= requested; `battle-combat.md:346`). Failure/err -> downgrade to attack, never drop (`:347`).
    - Executor: when command level <= 0 falls back to `SkillTemplate.Level` so +10 %/level scaling applies (`battle-combat.md:224`; code in
      `turn_executor.go` skill path - exact line **unverified**, `executeSkill` starts `:95`).
    - Other fallbacks to basic attack inside `executeSkill`: unknown skill, passive, on cooldown, self-HP cost unaffordable, not enough MP (`turn_executor.go:96-120`).
11. **Command wire shape**: `battleUpdateCmd([cmd0, cmd1?])`; entry 0 = own char, entry 1 = field pet (`commands_parse.go:3,38-42`);
    each `{tid, action, id, level}`; `tid` string/number -> string (`commands.go:337-348`); `id` -> SkillID, ItemSlot and SelectedPetID at once
    (`commands_parse.go:57-61`); `level` -> SkillLevel.
12. **Round cap**: `MaxRounds = 30` (`domain/combat/battle.go:73`) applies **only to PvP** (`NextRound` `:915-925`, `HasRoundLimit` `:927`).
    PvE has no round cap and no 10 min cut (owner 2026-10-31, `battle.go:8-11`, `battle-combat.md:743-745`). The 150-round auto limit is client-only.
13. **VIP gating**: none in the combat handlers or `SkillSetBattle`/`uif` (grep of `handlers/combat` for vip = 0 hits). VIP gate exists only for
    launcher autopilot kinds (`internal/infrastructure/config/store/autopilot.go:1-9`, `application/autopilot/catalog.go`). Flash-side VIP gating of the Auto button: **unverified** (not checked in `.as`).
14. **Items in auto**: server does nothing special; the client sends `ITEM (-60)` with `id` = bag row id (it resolves via `getItemNum`
    on template id `bs1/bs3/bs5` heal, `bs9` MP; pet `bs2/4/6`, `bs10`). Server resolves via normal item command path. Server-side item use in
    battle: `newBattleItemHandler` (`commands.go:176`).
15. **Auto-defence**: pure client logic (settings chain "auto-defence" in `Battle.as`, chain order from `battle-combat.md:193`:
    HP threshold -> MP threshold -> team heal -> pet heal -> auto-defence -> main attack skill -> fallback attack). The server has no auto-defence.
    (Exact auto-defence key not isolated: **unverified**.)

## 4. State / persistence

- Character: `Character.PMProcessData["interfaceData"]` (map) saved with the character (`interface_settings.go:301-342`) and mirrored into the
  `character_interface_settings` table via `settingsRepo.Upsert` (`:334-340`); login merges both (`login_payload.go:148-155,348-351`).
  Note `defaultInterfaceSettings` in `auth/settings.go:17-58` (used for persisted-merge) differs slightly from `defaultInterfaceData` below.
- Pet: **active pet** `Pet.Property` map keys `p6..p9`, `bt2/4/6`, `bs2/4/6/8/10` (`:344-363,365-392,451-485`). Only the *active* pet's settings are sent at login.
- Memory only: nothing; the in-progress auto toggle and the 150 counter live in the client.

| key | default | meaning |
|---|---|---|
| `ac`,`am` | 1,1 | client UI flags (sound/music-type, unverified meaning) |
| `he`,`hm` | 0,0 | (unverified) |

Extra defaults in `settings.go:17-58`: `pid,glid,p1 =0`, `dressHide,wingHide=0`, `flyEffect,hpmf,nlws=true`, `au=0`, `ubl=false`, `apvp=0`, `bt9,bt10,bs9,bs10 = 0`.
Persisted keys override defaults; a nil persisted value deletes the key (`settings.go:60-70`). `p2..p5` come from the character, `p6..p9` + `bt2/4/6`, `bs2/4/6/8/10` from the active pet override them (`activePetInterfaceSettings`, `:451-485`). Note `bt8`/`bt10` are never overwritten from the pet (bt not sent for 8/10).
Login shape: `interfaceData` is a flat `{key: number|bool}` object inside the `onChooseCharactor` payload (`login_payload.go:423`), values normalized to int (`normalizeSettingValue` `:510-528`; numeric strings -> int).

### skillSetBattle validation (`interface_settings.go:191-253`)

- `len(args) >= 4` else invalid args; `args[0]` skillId int, `args[1]` int (ignored), `args[2]` slot int, `args[3]` bool isPet.
- Pet: slot must be in {2,4,6,8} (`:218`), requires an active pet (else NotFound); skill must be learned at least (`PetHasSkillAtLeast`) or a variant of a learned one (stores the learned id; `:377-384`). Writes `pet.Property["bt<slot>"]=52`, `["bs<slot>"]=stored` (`:389-390`).
- Character: slot in {1,3,5,7} (`:225`); `HasSkill` or awakened variant else `ErrNotFound` (`:229-235,255-261`); writes `bt<slot>=52`, `bs<slot>=skillId` (`:237-240`). Returns `true`.
- Item slots, thresholds and pet slots 10: via `uif(key, value, isPet)` (pet flag true -> active pet property, `:94-95`) or `us({...})`. `uif` accepts **any** key without validation (`:79-84`); `defaultMoney`/`defaultGold` special-cased in `us` path (`:314-325`).
- `skillSetUserBar(skillId, _, slot 1..30)`: `st<n>=52`, `sid<n>` (`:113-157`).

## 5. Data tables

No data tables involved (settings are player state). Skill template columns used by the server-side auto helper: `target_type`, `type`
(1 CLOSE, 10 DEFENDER), `use_mp`, `use_hp`, `code_name` (family for level resolution). `data_tbl_skill` ids.

## 6. Push sequence

Auto adds no pushes of its own; each auto round is the normal `battleUpdateCmd` flow:
1. Waiting (not all humans submitted): reply `waitingForCommands`, no push (`commands.go:158-168`).
2. Round processed: `onCmdReady` to participants (`sendCmdReadyToParticipants`, `:279-281`) then `onBattlePlayList` broadcast (`:282`); on end `onBattleEnd` callbacks first
   (`sendBattleEndCallbacks`, `:236`) and the reply carries `battleEnded`.
3. Timeout round: same via battle service (`checkTurnTimeouts`).
Errors: battle gone -> `{success:false, error:"Battle is not active"}` silent (`commands.go:350-355`); bad arg type -> `ErrInvalidArgs`.

## 7. Launcher autopilot (brief)

`cmd/gameserver/autopilot_auto_cmd.go`: the server-side bot builds its own auto command from `interfaceData` (`bt1/bs1/p2`, `bs9/p3`, `bs7`;
`:47-51`), priority heal(if HP% < p2) -> MP item -> attack skill -> normal attack (`:81-108`), affordability check `:142-157`, a bare -110 added for the field pet (`:205-208`). Triggered after 8 s of waiting (`application/autopilot/battle.go:23,57-66`). Not part of the H5 in-game Auto; useful as a **ready-made reference** if the H5 server ever wants server-driven auto.

## 8. Port state (E:\magiccampus)

- **-110 not accepted**: `BattleAction.AUTO = -110` exists in shared (`packages/shared/src/battle.ts:8`) but `BattleCommandService.resolve` has no case and throws `invalidArgs('action')` in `default` (`server/src/modules/combat/battle-command.service.ts:49-50`); pets only allow ATTACK/SKILL/DEFENCE/TIMEOUT (`:28,95`).

- **Round cap**: `MAX_ROUNDS = 30` applies to PvE too (`round.ts:12,232`: PvE -> LOSE). Go removed this for PvE (2026-10-31). Gap; matters a lot for auto.
- **Timeout**: server 30 s deadline re-armed per round (`battle.manager.ts:8`, `combat.service.ts:217`); no 63/33 s anchoring.
- **Command parse**: `parseCommand` reads `{tid, action, id, level}`, entry 1 = pet (`battle-command.service.ts:98-111`). `level` is read but skill-level -1 resolution not verified in `resolveSkill` (**unverified**, not read).

- **Client**: `BattleController.ts` builds commands `{tid, action, id, level}` (`:140,159-164,206`) and `battleMenu.ts:56` registers Auto as a disabled button (`addButton('auto','Auto', null)`); `ui/hud/userBar.ts:33-37` Auto box is `notReady`; user bar slots are static (`:16-20`), no skill binding.

## 9. Port notes

Server (all in `server/src/modules/`):
1. `character` (or new `interface-settings` module): `InterfaceSettingsService` with Mongo field `interfaceData: Record<string, number|boolean|string>` on the character schema; `defaultInterfaceData()` copied from section 4 (st/sid 1..30, p2..p9=10, bt1..6=0, bs1..10=0 + ac/am/he/hm/c0..c3/maxView/apvp). Active pet extras stored on the pet doc `property` map (`p6..p9, bt2/4/6, bs2/4/6/8/10`).
2. Register `us(map)`, `uif(key, value, isPet?)` (generalise `pk.rpc.ts:uif`: keep `apvp` side effect, store the rest), `skillSetBattle(skillId, _, slot, isPet)` with validation in section 4, return `true`. Ownership via `SkillService`.
3. Login: include `interfaceData` = defaults merged with stored + active-pet keys in the `chooseCharactor` payload (add to shared `PlayerData`).
4. `BattleCommandService.resolve`: add `case BattleAction.AUTO:` -> treat as ATTACK on the first living frontline enemy (Go `turn_executor.go:47`); allow AUTO in `PET_ACTIONS`; tolerate missing/invalid `tid`.
5. Round cap: apply `MAX_ROUNDS` only when `pvp`.
6. Skill `level <= 0` -> template/learned level; pet: map base skill id to the pet's owned highest id of same `code_name` (Go `pet_skill_level.go:31-53`); invalid -> downgrade to ATTACK, never throw.

Client:
- Load `interfaceData` into a `GLOBAL_SETTING`-like store; port `battleAuto`/`battlePetAuto` chains (`Battle.as:94-563`) as a pure function (`client/src/game/battle/autoPlan.ts`) producing `{tid, action, id, level}`; `level: -1`. Wire the Auto button (`battleMenu.ts:56`) and a toggle with a 150-round counter (optional; Go patched it to unlimited). Cache last command so `-110` resends it like `Battle.as:1120`.
- Settings panel (BattleSettingPanel) writes via `skillSetBattle` / `uif` / `us`.
