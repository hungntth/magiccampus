## 3. Confirmed mechanics

### 3.1 Login award (`activity/login_award.go`, `internal/domain/loginaward/`, `application/loginaward/`)

The panel is the "Lợi ích → Thưởng đăng nhập" tab of `GameIntroPanel.as`. It has four boxes: free daily gift, 70 % sale item, 10 % continuous-login item, festival gift.

**Contract**

- `getTodayAward` → `{dailyAward, dailyDisc, contiLoginDay: [days, contiPlanId]}`. All three ids are **TBL_PLAN ids** (the client reads `ti/ii/n`); 0 = nothing.
- `getLoginAward` → Boolean: claims the free daily plan.
- `buyDiscountGift(shopSlotId)` and `buyContiGift(shopSlotId)` → Boolean.
  - **The shop slot id arrives as a string** (`"2007"`), so coerce it with `Number(...)`.
  - The client picks the slot itself: the first `TBL_SHOP_SLOT` (lowest id) with `type == ti`, `itemId == ii`, `st != 5`, `gold > 0`, `sid != 99`. The conti buy also needs `money <= 0`.
  - If no slot qualifies, the button silently does nothing. So the server only offers plans that resolve to such a slot, with first-slot `gold <= 100000` (this excludes the `8888888888` Tinh Hồn Thạch placeholder).
  - Prices: `ceil(slot.gold × 0.7)` (discount) / `ceil(slot.gold × 0.1)` (conti). Quantity 1, bound, **non-bound Vàng only**.
  - Confirm strings: `ACTIVEPANEL_S[6]` "Bạn xác nhận mua vật phẩm {item.name} với giá được giảm còn 70% so với giá gốc là {shopSlot.gold} vàng?" and `[7]` (the same with 10%) (`Language.as:768-769`).
  - Festival strings: `ACTIVEPANEL_S[4]` "Hôm nay là {festv.na}." and `[5]` "Hôm nay không phải lễ.".

**Plan pool**

- `TBL_PLAN` rows with `t = 1` and `st` from `1-2` to `1-16` (15 tiers × 10 items). Tier = `level/10 + 2`, clamped; weighted by `r`.
- `CONTI_GIFT_DAY = [8,18,28,48,68,88,108,128,158,188,218,258,308,358,408]`, then every 30th day past 408. The conti offer exists only on the milestone day itself.

**State** (legacy `character_login_awards`): `award_date, last_login_date, conti_days, daily_plan_id/claimed, disc_plan_id/bought, conti_plan_id/bought, feast_claimed_date`.

- The day rolls lazily on login (the streak counts even if the panel is never opened).
- Missing a day resets `conti_days` to 1.
- Claim order: atomic mark (`daily|disc|conti|feast`) → bag check → grant → for buys, debit gold. A failed grant clears the mark and takes no gold.

### 3.2 Gift code (`giftcode/handler.go`, `application/giftcode/service.go`, SQL `redeem_giftcode`)

**Client** (`AwardPanelAll.as` / `GameIntroPanel.as`): input with `maxChars 12`.

- It needs 1 free bag slot, else `AWARDCODEPANEL_S[0]` "Khoảng trống túi đồ không đủ!".
- It sends `uc(code)` only when the first character is N/G/D/A/O **or** the code is exactly 9 long (case-sensitive).
- No responder, no callback. Rate limit: one call per 31 s (`RPC_DELAY["uc"] = 31000`).

**Redeem checks, in order**: `not_found`, `disabled` (code or campaign `status <> 1`), `not_started`, `expired`, `already_used` (unique code × character), `player_limit` (`max_uses_per_player` per campaign, 0 = unlimited), `code_exhausted` (`max_uses`), `campaign_exhausted` (`max_total_uses`), `no_rewards`. Codes compare lower-cased.

**Rewards**:

- `item {item_id, count, template_table 29|19, bound (default true), quality}`;
- `exp`;
- currencies `gold`→gold, `gold_bind`→goldBind, `silver`→money, `silver_bind`→moneyBind, plus event points.

**Order**: consume the code → currencies + exp → save → items. An item that does not fit goes to the pending-gift store (`source = 'giftcode'`), claimable in "Thưởng hệ thống".

**Pushes**:

- success: `onAddMoney` per currency, `onUPP` (+ level-up) for exp, item pushes, then `onBlueMsg` "Nhận quà <campaign> thành công!" (+ the count sent to Thưởng hệ thống);
- refusal: `onSystemMidMsgOrNote` with a Vietnamese reason per status.

**Code format**: 4-12 characters, `A-Z 0-9 - _`, stored upper-case, starting with N/G/D/A/O unless exactly 9 long.

### 3.3 Pending gifts, home gift, online gift, SP gift, double exp

- **"Thưởng hệ thống"**:
  - `serchForGift` (Responder, Boolean) → true shows the item-2059 icon.
  - `searchGameGift()` (no responder) → the gifts come only through `onGetItemIdAward(jsonString)` (a JSON map of `{giftid, …}`).
  - `getGameGift(obj)` → `onMakeGiftCount(claimedKeys)`. These callback names were found by a bytecode scan of `CallBack`.
- **`gtg`** grants 2059 once per character, only while 2059 has award rows. It has none, so `serchForGift` stays `false` (legacy owner decision).
- **Online gift** (`activity/online_gift.go`):
  - Steps come from `game_tuning.online_gift_steps` `[{minutes, itemId, quantity, bound}]`. `minutes` is the wait from the previous claim; the first step counts from today's first login.
  - Push `onStartNewGift(waitMs, {plan:{ti:29, ii, n, b}, sp:false, warnType:196})` at login (H5: from `ActivityService.loginFields`, sent after the scene enter) and after each `takeNewGift`.
  - The claim is saved before the grant and rolled back if the grant fails.
  - Progress `{step, startedAt}` is persisted per UTC+7 day.
  - It is distinct from the H5 diary online gift (`getDailyOnlineAct`, 30 min); the two coexist (legacy has both).
- **Online gift strings**: success `onBlueMsg` "Nhận thưởng online thành công!"; `gtg` success `onBlueMsg` "Nhận túi quà trang chủ thành công!".
- **`getLoginAward` errors** (`onRedMsg`): "Phần quà này hiện không thể nhận." / "Nhận quà thất bại, hãy kiểm tra túi đồ.".
- **`takeSPGift`**: success `onBlueMsg` "Nhận Quà Đặc Biệt thành công!", failure `onRedMsg` "Túi đã đầy hoặc lỗi hệ thống!". It needs an open offer (in memory; `AdminDistributeSPGift` broadcasts `onStartNewGift` with `sp:true`). It pays once per character per offer, marked before the grant. Without an offer it refuses (it used to farm item 2005).

## 4. Decisions for H5

### 4.1 Event framework (shared by every timed event)

1. **`packages/shared/src/eventWindow.ts`** (pure, tested; builds on `dayKey.ts` UTC+7):
   - `EventWindow = {start: number, end: number, claimEndMs?: number}` (epoch ms);
   - parsers for the three legacy schedule shapes:
     - fixed range `"YYYY-MM-DD HH:mm:ss"` in Vietnam time (tichluy, exp_event windows, Halloween);
     - weekly (XCDS Mon→Sat, Đông Huyền Monday 19:00-22:00, dragon-ball weekdays 12:00-23:00);
     - anchored every-N-days (Kỳ Thạch);
   - `eventPhase(ms)` → `'before' | 'running' | 'claim' | 'closed'`; `periodKey(win)` = the start key (legacy: progress keyed by the start unix, so moving `start` resets progress; record it).
   - The existing `feast.ts` stays as it is (its own `at` format).
2. **`server/src/modules/events/`**: an `EventRegistry` service holds the event definitions `{key, activityId?, schedule, enabled}`.
   - Code defaults live in `events-config.ts`. Overrides are read **once at startup** from the imported `game_tuning*` collections (keys `tichluy_spend_event`, `exp_event`, `exp_multiplier`, `kythach_schedule`, `halloween_enabled`, `online_gift_steps`).
   - An optional `EVENTS_OVERRIDE` JSON in `server/.env` is read through `loadConfig()` (key names only; never print values).
   - A GM command `gmEvent(key, on|off|start|end)` (`requireGm`, chat `/event`) changes a definition in memory and persists it to a small `event_overrides` collection. This replaces the legacy dashboard; there is no admin UI.
3. **Per-character progress**: one generic `character_event_progress` collection `{characterId, event, periodKey, total, claimed: number[]}`, unique on (characterId, event, periodKey) (legacy table of the same name). It is used by consume, stage, Kỳ Thạch, XCDS and the anniversary claims.
   - Updates are atomic `$inc` / `$addToSet`. A claim is a conditional update `{claimed: {$ne: id}}` → **mark first, then grant, unmark on a failed grant** (the H5 rule from M8).
4. **Per-character feature state** (mini-game boards, welfare, findback ledger, MYTC, EM) uses the existing `character_features` store (`feature-store.service.ts`), one key per feature, with the legacy JSON shapes. Daily resets are lazy from the UTC+7 day key; there is no cron.
5. **Scheduled live events** (Kỳ Thạch, Đông Huyền, the exp-event announcer, the XCDS / anniversary period rollover) share one `EventTicker` (a 1 s `setInterval` in the events module) that calls registered phase handlers. Single process: no line logic, and the legacy `*_line_id` keys are ignored.

### 4.2 Money rules

1. **Vàng only** for every mini-game / event cost, whatever the payment radio says (legacy 2026-10-30, `currencies.md:87`). This applies to: login-award buys, welfare, card game, small game, EM, MYTC tabs 2/4, anniversary / summer / XCDS. Exceptions: MYTC tab 3 = goldBind; findback silver rows = bạc (`money`).
2. **One gold-spend seam**: add `GoldSpendEvents` (in `modules/events/`), called by a new `WalletService.spendGold(session, n, reason)` helper (non-bound gold, conditional `$inc`, `onAddMoney`/`onUPP` push).
   - Existing gold sinks are migrated to it in phase C (grep `gold:` decrements: mall, VIP `buyPm`, VIP shop, sign-in retro / crit, transport, offline exp, forge, pet slots…).
   - `RecordConsume` adds to every running consume / stage period.
   - Trade and future mail / auction moves never call it.
3. **Real-money top-up stays "not ready"**:
   - `gg`, `gp`, `exchangeAwardToGoldBind`, `exchangeAwardPointToGoldBind`, MYTC tab 1, `activeMYTCItem` and the "Nạp" links reply with `onMidNote "Chức năng nạp chưa mở."` (H5 string) and do nothing.
   - `getPointAward` still shows the rows (display only).
   - `exPoint` (điểm thưởng) stays 0.

### 4.3 Rewards and bags

1. Grant through the existing `ItemGrantService` / `RewardGrantService`. The bag is checked before any mark or debit.
2. **Bags with no `data_tbl_item_award` contents** must not be granted as dead items. These are:
   - 2059, 1541 (opened by its own rule), 5739-5768 (anniversary), 6637-6642 (XCDS), 3988 / 3551 (Halloween, own rule).

3. **Bag opening**: H5 has no generic `data_tbl_item_award` opener yet (only description parsing, M8). Phase A adds `ItemAwardOpener` in `activity-rewards/` (useItem hook for templates with award rows; types 29 / 19 / 30 money / 35 …, as far as the rows need). If M11 ("bags" in the plan name) ships one first, reuse it (open question 1).

## 11. Risks and open questions

**Open questions** (for the user):

1. **Bag opener ownership**: does M11 (plan 14, "bags") deliver a generic `data_tbl_item_award` opener? If yes, phase A reuses it; if not, phase A adds `ItemAwardOpener`.
2. **Overflow sink**: when a reward does not fit the bag, refuse ("Túi đồ đã đầy", legacy for most events), or mail it once M11's `sendSystemMail` exists (legacy did this for gift codes via the pending store)? Proposal: refuse everywhere except gift codes, which go to mail when available and the pending store before that.
3. **`soulPnt`**: is Pha Lê already a balance in H5 (M7 train soul)? The card game must credit the same balance the train-soul tab spends. Also confirm the Go `ClientKey` ids for `smP14` / `xcds2403p`.
4. **Event windows**: the seeded Tích Lũy window ends 2026-11-11 and the dated consume / stage rows end 11-05 / 11-06. Keep the legacy dates (claims open just after deploy), or set fresh H5 windows through `/event`?
5. **Gift-code creation**: a tool script plus a GM command enough, or should codes also be importable from the legacy Postgres campaigns (none are in the seeds)?
6. **Mongo transactions**: the compose Mongo runs standalone (no replica set), so gift-code redeem and multi-document claims use conditional updates + compensation. Acceptable, or switch compose to a single-node replica set?
7. **Seasonal default**: should the anniversary / summer / XCDS hubs be on by default (legacy: always open), or off until the user starts a season with `/event`?
8. **Phase F**: Kỳ Thạch and Đông Huyền need scene partitioning, scripted spawns and league maps. Are they wanted at all, or dropped to non-goals?

**Risks**:

- **Gold-sink migration (phase C)** touches many modules. Missing one only under-counts consume totals (no money loss); list the sinks in the notes.
- **Client-trusting mini games** (small-game results, the anniversary client-side rules): the legacy accepted the client's win flag. H5 keeps that parity with the server-side caps, so payouts are bounded by daily limits.
- **Unverified legacy assumptions are carried over**: Wasteland pipe openings, card-change cost, PM-right-30 unit, dragon weekday mapping, small-game amounts. Each is listed in its memory doc and stays tunable in shared config.
- **File size**: 26 + 17 RPC families must be split per game to stay under ~300 lines per file.
- **Exp multiplier**: it changes progression balance server-wide. It defaults to ×1 (`exp_multiplier "1.0"`, `exp_event.enabled false`), and only GM toggles change it.
