## 2. Confirmed mechanics

### 2.1 Relationships, friend request, enemies, intimacy (14.1a)
- Wire relationship types (Flash `GamePredef.RELATIONSHIP_TYPE`): 1 friend, 2 black, 3 enemy, 4 couple, 5 tutor, 6 brother.
  Go stores domain = wire − 1 (`handlers/social/client_contract.go:12-23`). H5 already uses wire values; keep that.
- Caps `RELATIONSHIP_SIZE = [120, 30, 20, 100]` (`GamePredef.as:890`): friend 120, black 30, enemy 100.
- Only types 1..3 can be added by name (`social/relationships.go:23`). One non-black row per pair: friend, enemy, couple, tutor
  and brother exclude each other ("Người này đã có quan hệ khác với bạn, hãy xóa quan hệ cũ trước!"). Friend ↔ black exclusion
  stays as H5 does it (row swap).
- Refusal texts (`application/social/service.go:219-285`): "Bạn bè đã tồn tại!", "Danh sách đen đã tồn tại!", "Kẻ thù đã tồn tại",
  "Người này đã trong danh sách đen, không thể kết thành bạn!", "Người này đã trong danh sách bạn bè, không thể đưa vào danh sách
  đen!", "Danh sách đã đạt giới hạn %d người, vui lòng xóa bớt trước khi thêm!".
- Friend request (`handlers/social/friend_request.go`): A's `addRelationByName(B, 1)` writes only A's row. B (if online) gets
  `onBeFriendOfOther({id, otherId: A, name: A, alreadyFriend})`. `alreadyFriend` = B holds a friend/couple/tutor/brother row
  toward A → client note CALLBACK_S[96] "{name} kết bạn với bạn."; otherwise Alert [97] "{name} kết bạn với bạn, bạn có muốn kết
  bạn với người chơi này không?". YES → `addRelationByName(A, 1)`; NO → `refuseToAddFriend({targetId: A, selfName})`.
  The server (refuser = session character; silent unless A really holds a friend row toward B) pushes
  `onRefusedToAddFriend({id: B, name: B})` to A → CALLBACK_S[98] "Tiếc quá, {name} đã từ chối kết bạn với bạn.". A's row stays.
- Intimacy is per direction on each row. `onSetClose(otherId, otherName, num)` (3 args): num > 0 = new total
  (CALLBACK_S[77] "…tăng lên: {num}"), num < 0 = a drop by −num ([78] "…giảm xuống"), 0 = reset ([103]).
- `useIntimacyItem(targetName, qty, templateId)` (`item/intimacy_item.go:41-100`; Flash `Player.as:1077`): 32 Bó Hoa Hồng To
  +660, 1302 Chocolate +60, 1303 Hoa Hồng +60, 1315 Hộp Chocolate +660, × qty, both directions, on existing non-enemy rows only.
  Order: resolve target ("Không thể tặng cho chính mình.", "Chỉ có thể tặng cho người trong danh sách bạn bè." unless
  friend/couple/tutor/brother, "Không tìm thấy người chơi này."), consume qty ("Không đủ vật phẩm."), bag pushes, add, `onSetClose`
  to the online sides. "Người khác giới" on roses is not enforced (Go).
- Team intimacy: +6 per player at most once per 55 s (`TeamBattleIntimacy`, `TeamIntimacyInterval`): from a won team battle
  (toward same-side characters) and a 60 s online-team tick (toward the other online members). Only on existing rows.

### 2.2 Teacher / student (14.1b)
- Login fields: `ti` (teacher id, "-1" none), `tn`, `tl` (rank 0–6), `tp` (points), `ll` ("<last reported level>|<exp>").
- Ranks = `TEACHER_TITLE` 0 Không có … 6 Vạn thánh chi sư; titles 1–6 = rank (`data_tbl_title` 1–6, buffs 546–551).
  Students per rank `STUDENT_NUM` = 0/5/10/15/20/25/30. Upgrade gate `tp >= [-, 2e5, 8e5, 2e7, 2e8, 1e9][tl]`, points not spent
  (`domain/mentor/mentor.go:46-47`; "Điểm chức nghiệp chưa đủ để thăng cấp!").
- Rank 1 comes from quest 692 "Lần Đầu Làm Thầy" (NPC 547, Lv 30) turn-in or the NPC 49 flow; lazy promotion of earlier turn-ins.
- IM pairing (`application/mentor/rules.go:41-82`): no self, student has no teacher, no reverse link, teacher rank ≥ 1, teacher
  Lv ≥ 30 and ≥ student level (gap 0), free slot, the pair has no block and no row other than friend/tutor.
- `findTeacher(name)` → reply `{t:2, f}`; `findStudent(name)` → `{t:1, f}`. f: 1 waiting, 2 offline, 3 not found, 4 level,
  5 already has teacher, 6 full / not eligible / self, 8 (findStudent) target is your own teacher. On f 1 the target gets
  `onFindTeacher({t:1, i: studentId, n})` / `onFindStudent({t:2, i: teacherId, n})` (warn icon WARNCANVAS_S[2]/[4]).
  Requests live 5 min in memory, keyed by pair and direction. Expired: "Lời mời sư đồ đã hết hạn hoặc không tồn tại!".
- Accept (`acceptStudent(studentId)` / `acceptTeacher(teacherId)` / `confirmTutor()`), push order (`mentor/handler.go:158-195`):
  teacher `onMakeTS({t:1, i: studentId, n, l: studentLevel})`, student `onMakeTS({t:2, i: teacherId, n, l})`, (NPC promote)
  teacher `onUPP({tl:1})` + title 1, then both `onInitViewImC`. Tutor rows (type 5) both directions, keeping friend intimacy.
- NPC 49 Quản Lý Tiến Cử (type 16, map 100): `npcFuncOther(49, 1)` → `tutorFuncAlert({i: leaderId})` → NPCFUNCOTHER_S[26]
  "Xác nhận nhóm trưởng hiện tại là người tiến cử?" → `confirmTutor()`. Caller is a non-leader member, leader online, leader Lv ≥ 30,
  member Lv ≤ 20. NPC pairs are locked until the student is Lv 30 ("Quan hệ tiến cử tạm thời không thể giải trừ (đồ đệ cần đạt cấp 30)!").
- `delST(studentId)` / `delTeacher()`: `onDelST({t:1, i: studentId, n})` to the teacher, `{t:2, i: teacherId, n}` to the student,
  both `onInitViewImC`; rows go back to friend rows when they were friends before (`fb`), else are deleted.
- `reportTS()` → `{t:2, f, ll}` (f 1 ok, 2 no teacher, 3 nothing to report, 4 teacher offline); teacher gets
  `onReportTS({t:1, i, n, tp, ll})`. Gain = floor(Σ levelExp(last+1..cur) × 10 %) to the teacher `tp` and the pair exp; student
  honor += levels gained. No items (the Tiến Cử bags 2020/1844/1845 have no award rows). No graduation.
- `initTS()` → `onInitTS([{id, name, ll, honor}])`. `upTeacher()` → `onUPP({tl, tp})` + title = new rank, reply `{t:1, tl, tp}`.
- Refusals go as `onSystemSay` with a nil reply (Go). Flash refuses `findStudent` locally while `tl == 0` (IMPANEL_S[37]).

## 3. Decisions for H5

1. **Relationships** stay in `relationships` with wire types 1..6 and a new `intimacy` field (default 0) per row. Caps: friend
   120, black 30, enemy 100. Couple, tutor and brother rows are written only by their features. Deleting a tutor, couple or
   brother row through `delRelationship` is refused ("Hãy giải trừ quan hệ ở chức năng tương ứng"; Go let it desync).
2. **Friend request prompt** ported as in §2.1 (`onBeFriendOfOther`, `refuseToAddFriend`, `onRefusedToAddFriend`). The H5 client
   shows the Yes/No prompt; offline targets get nothing.
3. **Intimacy**: gift items through `useIntimacyItem` (the bag "Dùng" action on templates 32/1302/1303/1315 opens a name + quantity
   prompt), team gains +6 / 55 s from won group battles and a 60 s online-party tick. No opposite-gender rule (Go).
4. **Mentor** state: a `mentor_links` collection (one row per student, unique `studentId`) plus `tl`/`tp` in a
   `character_features` row `mentor` (FeatureStoreService). Pending requests and NPC drafts in memory (5 min / 60 s).
   Reports give points only (no bags, as Go). Rank 1 from quest 692 turn-in (quest turn-in hook) or the NPC 49 flow.
5. **NPC script menus**: Brotherhood and marriage need the legacy `onList(npcId, npcName, content, options[{label, func}])` push and
   the `npcScript(funcId)` RPC (`handlers/npc/menu_hooks.go`, `npc_interaction.go:55-70`). If M10 (dungeons) has not already added
   them, Phase B adds an `NpcMenuRegistry` in `modules/npc/` (providers by npc id, the "Nhiệm vụ" entry prepended when the NPC has
   quests) and a client `onList` dialog. Text replies use `onNpcMsg(npcId, text)`.
6. **Brotherhood** state: `brotherhoods {_id (counter), title}` + `brotherhood_members {characterId unique, brotherhoodId,
   joinedAt}`. Ceremonies in memory (60 s). Title 153 through TitleService; `broT` added to `SceneCharacter`.
7. **Marriage** persisted in Mongo: `marriages` (partial unique on active partners), `marriage_seeking`, `marriage_requests`
   (30-day TTL index on `addDate`), `wedding_bookings`. The NPC tier pick is in memory (30 min); a booking without a tier pick is
   refused ("Hãy chọn loại lễ đường ở Cupid hoặc Nguyệt Lão") instead of Go's possible tier-0 booking.
   - Single line: `line` is accepted and stored, the only value is H5's line 1; the 30 min gap is global.
   - Hall exit: on close, guests in maps 63/64/65 go back to the recorded origin (fallback map 34 safe point), also at login.
   - Divorce consumes the card **after** the marriage is ended (Go consumed first and could lose the card).
   - Couple skills (3305 / 3774) are granted and revoked, but their battle effects (partner heal / revive) are deferred to the
     combat skill pipeline (§9).
   - Scope cut: candy scatter, hall NPCs 1493/1558, lucky draw, parade guides, flight (`onBeginWeddingFly`) are non-goals.
8. **Rooms (14.3)**: room fields live on the in-memory party (`PartyBook`); no Mongo. Fixes over Go:
   - refusals are real notes (`RpcException.forbidden`), not Go's 500 strings;
   - `onMemberLeave(cid)` carries the bare cid; `onSetRoomHost(cid)` is sent on every leader change of a room (also on leave);
   - `setRoomConfig` persists level-only changes and the push carries `minLevel/maxLevel` too (extra keys are harmless);
   - an expired room (now > `scheduledAt` + 30 min, H5) is dissolved with GROUP_RECRUIT_PANEL_S[35] "Thời gian hẹn trước đã
     hết, nhóm mời giải tán！" — Go never did this; if the user prefers Go parity, drop it (open question 10);
   - `roomChat` goes through the chat rules (ban gate, 55-char cap, the shared 1100 ms limit, `normalizeMessage`).
   - `groupListOfMap(mapId)` returns the parties whose leader is on that map (Go returned `[]`).
   - `getGroupMemberPosistion(cid)` answers only for a member of the caller's party, from the live session position, in the
     legacy ×10 units; `getCharLeaderClient(cid)` returns a boolean.
   - `reqAddGroup` is a stub that forwards to the `groupRequest` flow (no unapproved join); `groupReqSuccNotice` returns null.
9. **Duel invite**: the six `pk*` invite RPCs are registered as stubs that throw `RpcException.forbidden('Chức năng chưa mở')`
   (no Flash caller, no handler for their pushes); this closes the roadmap count without a dead feature.
10. **3v3**:
    - Single process: no line resolution; `checkPVPLine` checks open + level.
    - Run state in memory (`ThreePvpService`, 1 s tick, UTC+7 clock via `dayKey.ts`), points/medals persisted in
      `event_progress {characterId, event, periodKey, total, claimedTiers}` (new, unique per triple), currency `threePvpPnt: 225`
      added to `CURRENCY_IDS`.
    - Battles: `PvpService.startSystem(sideA, sideB, mapId)` generalises the duel to ≤ 3 characters + pets per side (the
      group PvP slot layout above), no rewards, HP/MP restored to max at settle, a battle-end hook for the scorer.
    - Claim-then-credit is done as a guarded Mongo update that is rolled back if the credit fails (Go burnt the claim).
    - Partial rooms (1–2 members) are allowed (owner rule 2026-10-30), with the `armLeader` pushes.
    - GM: `gmThreePvp(minutes)` `@Rpc(..., { requireGm: true })` opens a test window (default 15, min 5); no HTTP admin.
11. **Chat ban**: 100 gold to ban (20 min, or 12 h with the 4th arg), 100 gold to lift via `/huycam`; whispers and `chatGM` are not
    blocked (Go owner rule 2026-11-02). Persisted in `chat_bans {characterId unique, bannedBy, bannedByName, expiresAt}`.
12. **GM chat commands**: H5 keeps its `requireGm` RPCs (`/go`, `/buff`, `/grant`); the legacy chat-typed `/add`, `/nap`, `/stat`
    are not ported (`/grant` already covers items, currencies and levels; `/nap` is a payment tool). `chatGM(message, playerId,
    gmName)` is ported as a GM inbox: the message (session character as sender, `playerId` ignored, 500 chars max) is stored in
    `gm_messages` and delivered as `onWisper`-style lines to online GM accounts (gmLevel > 0); the sender gets a note "Đã gửi tới
    GM". No `onChatGM` push (Flash has no handler).
13. **Chat panel header**: `createChatPanel` / `getChatPanel` return the header object (Responder); the H5 private chat window
    calls `getChatPanel` on open to show level/class/icon. Headline: in-memory board with login replay; the H5 chat box shows the
    strip above the log. Emoji: a picker inserting the Flash emotion codes (format from `TextUtil.encodeChatMsg`, to be read from the
    served SWF by the implementer; if unreadable, an H5 `:eN:` code set rendered client-side) — the server stays a relay.
14. **Cross-server (14.6)**: not implemented (§12).
15. All new RPCs are registered without `quiet`; state-changing ones are `forbidInBattle`.
